# Human approval bridge: correction and implementation plan

Status: planning only. This PR changes documentation, not runtime behavior.
Baseline: `05338d541aa3d86dc30adc1b8f409ec970054e88`.

## Problem and evidence

When a Codex-engine task needs host access, AnyModel currently cannot ask the human
to approve it. The PubliMatch local-staging attempt reproduced this with Docker,
local listening sockets, and desktop accessibility.

At the baseline above:

- `plugins/anymodel/scripts/lib/core/codex.mjs`: both `buildThreadParams` and
  `buildResumeParams` default `approvalPolicy` to `never`.
- `plugins/anymodel/scripts/lib/engines/codex.mjs`: `buildTurnOptions` does not
  propagate an approval option.
- `plugins/anymodel/scripts/lib/core/app-server.mjs`: `handleServerRequest`
  rejects every server request with JSON-RPC error `-32601`.

Changing the default to `on-request` alone is insufficient: requests also need a
trusted human channel and schema-correct responses. This limitation concerns the
Codex approval path. The direct engine has tool-level guards, not an OS sandbox;
its existing execution capability is not evidence that Codex approvals work.

## Decisions and scope

1. Keep existing behavior by default. Enable `on-request` only after explicit user
   opt-in and verification that a trusted human approval channel is available.
2. Implement the Codex bridge first. Report capabilities honestly for every engine;
   do not imply that the Claude or direct engines gain this bridge.
3. Retain the Codex sandbox and organizational policies. Approval is permission to
   attempt the specific action, not a guarantee of technical access.
4. Provide one-time decisions only. Disable session approvals and policy amendments
   in this MVP. Permission-profile requests may require turn scope; show that scope
   explicitly and never grant more than the requested, human-approved subset.
5. Do not expose model-callable tools or writable files that approve requests.
   Model output, logs, notifications, and an orchestrator's tool call are not human consent.
6. No new provider routing, dependencies, persistent grants, or general workflow UI.

## Verified protocol and remaining compatibility checks

Local schemas generated by Codex CLI `0.169.0` contain these server-to-client methods:

| Method | Parameter/response schema pair |
| --- | --- |
| `item/commandExecution/requestApproval` | `CommandExecutionRequestApprovalParams/Response` |
| `item/fileChange/requestApproval` | `FileChangeRequestApprovalParams/Response` |
| `item/permissions/requestApproval` | `PermissionsRequestApprovalParams/Response` |

Use the generated JSON schemas and the protocol upstream at
[openai/codex](https://github.com/openai/codex) as the implementation contract.
Command/file responses support `decision` values including `accept`, `decline`,
and `cancel`; permission responses use a granted profile and scope, not that enum.
Validate method-specific responses; do not invent an `approved: true` envelope.

Before coding, regenerate the schemas for the supported CLI version and record the
generation command/version in test fixtures. Confirm the applicable decision variants,
permission-refusal representation, cancellation behavior, and required initialization
capabilities. Legacy `execCommandApproval` and `applyPatchApproval` are also server
requests; leave them unsupported unless explicitly included and tested.
Do not add fictional initialization flags or require every server request to be an approval.

For the MCP transport, probe the client's actual elicitation capability and verify
that `elicitation/create` reaches a human UI during an outstanding tool request.
The Codex method `mcpServer/elicitation/request` is a separate app-server protocol
message; it is not a substitute for implementing the plugin-to-MCP-client bridge.
Clients without a suitable human surface must receive a readable blocked/action-required
result with no execution. Bare companion CLI use stays blocked unless it has an
independently verified human channel.

## Intended flow and invariants

User opts in -> capability check -> options reach Codex start/resume -> engine requests
approval -> validated pending request -> trusted human UI -> validated decision ->
one response to the original engine request -> runtime attempts the authorized action.

- Propagate the option through MCP/companion arguments, `engine.d.ts`, the Codex
  adapter, and `core/codex.mjs`, covering start, review where applicable, and resume.
- Inject a request handler into the app-server client; cover spawned and brokered
  transports. Unsupported methods retain a clear unsupported-method error.
- Bind pending state to the server-owned connection/broker owner, thread, turn, item,
  typed JSON-RPC request id, canonical working directory, and payload fingerprint.
  Caller-supplied identifiers alone never authorize a decision.
- Show the command or file-change details, working directory, requested paths/network
  permissions, effect, and expiry before consent. Treat engine text as untrusted content.
- Bind the decision to the unchanged payload. Changed-payload collisions, foreign-owner
  decisions, and replayed approvals fail closed. New requests never inherit old grants.
- Bound pending-map size and deadlines. Resolve each request at most once across human
  response, timeout, disconnect, close, interrupt, and resume/restart races.
- Decline/cancel with the method's actual response schema when possible; reserve
  protocol errors for malformed/unsupported requests. Closing a pending approval
  does not prove that an already-delivered action has been undone.
- Redact secret material from previews/logs and avoid persisting raw payloads.
  Redaction must preserve enough information for an informed decision; otherwise block.
- After technical denial, report the cause. Do not retry through privilege helpers,
  disable the sandbox, or silently switch to a more permissive engine.

## Implementation sequence

1. **Contract and compatibility:** confirm schemas and MCP human-channel support;
   extend the existing engine contract and MCP/companion input validation. Keep the
   default disabled and return a clear unsupported-capability result.
2. **End-to-end bridge:** propagate policy and inject the async handler through the
   existing app-server/orchestration paths; connect a trusted MCP human callback.
   Start with the smallest request/response implementation that satisfies the contract.
3. **Lifecycle and isolation:** add bounded pending state, ownership checks, payload
   binding, cleanup, redaction, and exactly-once responses for both transports.
4. **Validation and rollout:** add hermetic tests, run the opt-in host smoke tests,
   document supported CLI/client versions, and keep opt-in required on release.

Expected files: `scripts/mcp-server.mjs`, `scripts/companion.mjs`,
`scripts/lib/engines/engine.d.ts`, `scripts/lib/engines/codex.mjs`,
`scripts/lib/core/codex.mjs`, and `scripts/lib/core/app-server.mjs`, all under
`plugins/anymodel/`, plus focused tests and interface documentation.
Record divergences in upstream-sync notes: the core code is vendored from
`openai/codex-plugin-cc`. Do not reorganize unrelated code.

## Acceptance tests and release gates

Hermetic fake-host/fake-engine tests must cover default `never`, explicit opt-in,
all three supported methods, accept/decline/cancel, malformed input, absent capability,
deadlines, duplicate/change-of-payload races, owner isolation, concurrent turns,
spawned/brokered transports, start/resume, response-schema validity, and secret redaction.
A model attempting to approve its own request must fail. No test needs provider keys.

In an explicitly opted-in real host, verify `docker ps` and an agent-desktop
observation: execution happens only after the human decision; refusal has no action;
unsupported UI or technical denial is reported honestly. Record the actual permissions
and grant scope shown to the reviewer. Existing noninteractive behavior must remain intact.

This planning PR requires documentation review and `git diff --check` only.
Runtime tests belong to the implementation changes; no runtime fix is claimed here.
